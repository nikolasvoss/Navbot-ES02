# Case file A/B: standing oscillation and voltage dip on balance activation

Status: open

As of 2026-09-27. This note is an inventory, **not a root-cause determination**. The raw traces cited here are no longer in the current workspace; their file names remain as historical evidence references. Statements from user reports, serial logs, an oscilloscope measurement made by the user, and the local source code are separated below. The hardware description in the [hardware overview](../../docs/robot/hardware/system-overview.md) and the [hardware reference](../../docs/robot/hardware/electronics-reference.md) mainly describes the PCB design, not every property of the assembled board.

**Separation:** The standing oscillation (A) and the voltage dip or shutdown on activation (B) partly occurred in the same test, but for now they are two observations with an unresolved cause-and-effect relationship. The tipping during **fast driving** reported later is Case C in [Case C](2026-09-27-drive-instability.md). A case overview is in [problem-map.md](2026-09-27-problem-map.md). Stable standing tests do not show stable fast driving; the absence of a voltage dip while standing does not explain the earlier voltage dip.

## Problem and timeline

- The user reports that the Navbot-ES02 worked about two days ago and oscillates while standing after a single flash of the GitHub default firmware. The exact earlier firmware state, the earlier controller settings, and the test conditions at the time are not documented. The timing does not establish a firmware cause.
- When remote control channel CH5 is set to position 1, the leg servos vibrate briefly, according to the user's observation. The motors then turn off, and the signal strength shown on the remote control drops to zero. Whether the ESP32 restarts, the receiver supply fails, a failsafe triggers, or something else happens was not measured directly.
- The user separately reported that the calibration commands `C1` and `C-1` moved the addressed servo in the same direction. There is no independent motion measurement or established command interpretation for this.
- For the further controller analysis, the user provisionally wants to assume working hardware, because the robot ran before. This is a **working assumption of the user**, not a verified test result for the battery, contacts, servos, motors, or board under today's load.

## Findings from the **local source code**

- [OllieFOCdrive.ino](../../src/ES-02/OllieFOCdrive/OllieFOCdrive.ino) sets `SENSOR_DIAGNOSTIC_MODE=0`. `RXsbus()` maps CH5 to the values 0, 1, and 2. Both active modes 1 and 2 pass through `PIDcontroller_posture()`. Mode 1 uses angle controller values P=66, I=222, D=1; mode 2 uses P=9, I=222, D=0.11. The speed controller values and the touch behavior also differ. The mode comparison therefore does **not** isolate a single PID coefficient. With a physical three-position switch, the transition from 0 to 2 and back may briefly pass through 1; such transition lines must not be evaluated as mode 2 behavior.
- `MyPIDController::compute()` computes the D term from the error difference divided by `dt`. In this configuration, the angle controller is not D-filtered. The local source code was extended with initialization of the previous angle error at power-on and a limit of both motor targets to ±`motor.velocity_limit` (here 88). The targets at exactly ±88 visible in the most recent trace are **consistent** with this change; there is no read-back hash or other verification of the binary image currently flashed.
- The wheel speed estimator divides the angle difference by a fixed `0.01f`, while the associated control loop runs from `time_dt >= 0.001f`. The actual step time during the error sequence was not measured. Correcting this scale would change the speed feedback and therefore the controller action; it has not been done so far.
- The code uses SimpleFOC in voltage mode for the wheel motors and sets `motor.voltage_limit=8.4` and `motor.current_limit=5`. Without current measurement, no actually limited battery current can be derived from this. `Voltage:` outputs below 7.4 V are a warning message in the code; the shutdown that is commented out there is not executed.
- The control loop also computes `BodyX` from the measured wheel speed; `BodyX` feeds into the leg kinematics and therefore into the servo target angles. The observed servo motion must therefore not be assumed to be either an independent defect or merely a passive consequence of the motor oscillation.
- After the CH5=2 test, a `K56`/`CTRL` trace was added to the **local** source code. It outputs the yaw gyro, turn command, angle and yaw controller terms, and both motor targets together. `capture_balance_trace.py --trace-mode 56` can record it. The sketch compiled successfully with the documented ESP32-S3 FQBN. The subsequent user flash is functionally confirmed by the valid `K56` baseline trace; no binary hash was read out. The older `balance-trace*.log` files were created with the previous `K55` firmware.
- In the active two-wheel controller, `YawPid.P=110` applies; in manual roll mode its I term is off. With `BodyTurn=0`, a measured rotation rate of about 0.8 rad/s already gives a yaw output of about 88, which is the order of magnitude of the motor target limit. The CH5=2 trace also shows large angle outputs at the same time. Too high a yaw gain is therefore a testable hypothesis, not yet the established cause.
- For an isolated comparison, `DIAGNOSTIC_DISABLE_YAW_PID=1` was set. This sets only the yaw contribution to the motor targets and the `K56` output to zero in the active two-wheel path; gyro Z and yaw error remain visible in the log. The first sketch with this change compiled successfully with `esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=default` and was then flashed by the user. That was an earlier test state; this switch is no longer present in the current local source code. The later live-tuning base loads yaw P/I=0 in setup.
- The user flashed and tested the yaw-off comparison; `K56` shows, as expected, `yaw_output=0` and equal motor targets. Afterwards, `K57`/`BAL` was added for `Angle_Pid.outP`, `outI`, `outD`, `BodyX`, motor targets, and the board voltage minimum, to investigate the remaining back-and-forth oscillation without further gain changes.
- The user then flashed `K57` and recorded `control-ch5-2-balance-pid.log`. In 446 evaluable CH5=2 partial lines from 0.5 s after activation, roll is between −3.60° and +3.25°; RMS of the controller terms: P ≈ 16.8, I ≈ 5.7, D ≈ 16.9. This evaluation checks `outP≈9×angle_error` in each partial line; motor targets are often truncated because of serial concatenation. The I term is therefore clearly smaller than P and D in the measured section, and P and D are of similar size; the log data do not show whether D drives or damps. `BodyX` stays below 0.005 in absolute value in the readable lines. Raw board voltage minimum in the running section: 5.636 V.
- For the P comparison, `DIAGNOSTIC_REDUCE_ANGLE_P_WITH_TOUCH=1` was temporarily set. Only the effective CH5=2 angle P value dropped from 9 to 6; I, D, and the disabled yaw contribution stayed the same. The switch was afterwards removed from the local source code and replaced by a live-tuning base (see below).
- The user flashed the P=6 build and recorded `control-ch5-2-angle-p6.log`. `angle_out_p≈6×angle_error` confirms the effective gain in 477 readable CH5=2 partial lines. From 0.5 s after CH5=2 (452 partial lines), roll is −0.74° to +0.58°, and the RMS value of the sum of angle P/I/D is about 3.87 motor target units; in the previous P=9 trace it was −3.60° to +3.25° and about 21.85. The raw board voltage minimum in the settled section is 7.441 V, compared with 5.636 V in the previous test. The tests are not a randomized A/B measurement and started from different tilts (before activation about −5.4° at P=6 versus −4.5° at P=9); nevertheless, the improvement is large and consistent. The user confirmed that the robot stood on its own and only trembled very slightly.
- Serial live tuning is available in principle: `U1` sets `PidParameterTuning=1` and prevents `PidParameter()` from reloading the gains from mode constants during the active control step; `PP<value>`, `PI<value>`, `PD<value>` change the angle controller (`AnglePid`) via SimpleFOC `Commander`, and `YP<value>`, `YI<value>` change the yaw controller. `PP`/`YP` query the values. `U0` enables automatic gains. Gain changes are not written to NVS by `FlashSave()` and are lost after a restart. The capture script supports `--interactive`, logs commands in the same log, and sends only gain, `U`, and `K` commands.
- The first live-tuning test in `control-live-yaw10.log` began with CH5=0; at `16324 ms`, CH5=1 was recorded, and at `16365 ms`, still before CH5=2, an angle output of +408 and motor targets +88/+88, accompanied by a raw board voltage minimum of 5.340 V. At `16466 ms`, CH5=2 was recorded; the active section up to about `17216 ms` shows angle outputs mostly around +15 to +38, yaw output mostly 0, and raw voltage of at least 7.432 V in the readable partial lines. The user set CH5 back to 0 manually; the log briefly shows CH5=1 and then 0. Raw voltage minimum after switching back: 4.728 V at `17277 ms`, while the output motor targets are 0; at the same time, high servo target angle ranges up to 27° were recorded. The log then continues for over `52 s` without a visible renewed `system run.` message or brownout message. `U1` was sent only at about `31.5 s` and `YP10` only at about `41.6 s`, that is, **after** this one recorded CH5=2 section. The test therefore does not check the effect of yaw P=10. The current is not measured; a current peak as the cause of the voltage dip remains a hypothesis. The original instruction, to activate CH5=2 first to initialize the gains, skipped the risky intermediate mode CH5=1.
- The preloaded live-tuning state corrects this initialization: `PidParameter()` loads CH5=2 gains with angle P=6 and yaw P/I=0 in setup, `PidParameterTuning` starts at 1, and during this diagnostic mode the brief CH5=1 passage also uses the same gentle gains. `PP` and `YP` can therefore be read and changed at CH5=0 before the motors are activated. The state compiled successfully with the documented FQBN (`/tmp/navbot-live-tune-preloaded-build`) and was then flashed by the user. With `DIAGNOSTIC_LIVE_TUNING_DEFAULTS=0`, the original modes apply again.
- The user flashed the preloaded state and recorded `control-preloaded-ch5-2.log`: `PP` reported 6 and `YP` reported 0 before CH5 was activated. Among the readable `CTRL` lines, CH5=2 was active from about `28370` to `32067 ms` (143 evaluable partial lines). Because of serial corruption, no complete CH5=1 line was recognized during the switch-through; this does not mean that the switch skipped the mode. At the first readable CH5=2 value, roll was −11.39°, the angle controller output −64.89, and the raw board voltage minimum 6.964 V. In the section from 0.5 s after activation (124 readable partial lines), roll was between −2.08° and +1.82°, the median of the absolute value 0.31°, and the raw board minimum 7.097 V. The earlier dips to 5.34/4.73 V were not observed again in this active section. After the recording ended, the user switched the robot on again and reported that it stood on its own very stably and reacted to light pressure in either direction with a matching driving movement; this second test is **not** in the log. The yaw control was at P=0; its effectiveness has not been checked again.
- In the following yaw-P=10 test, at CH5=0 `PP=6` and `YP=0` were set, then `YP10`; the command was answered before CH5=2 (`P: 10.000`). CH5=2 stayed active from about `26891` to `35920 ms`. In 182 fully readable lines that were consistent with `angleOutput ± yawOutput`, roll was between −0.39° and +0.41°, gyro Z between −0.049 and +0.097 rad/s, yaw output between −0.53 and +0.94, both motor targets below an absolute value of 6, and the raw board voltage minimum 7.518 V. For readable lines with a sufficiently large yaw error, `yawOutput/yawError` was about 10, confirming the effective live gain. No visible restart in the log; the robot's later attitude at CH5=0 is not relevant for the balance assessment. **The raw file was overwritten by the user under the same name during the following P=5 test; the numbers cited were evaluated before that and can no longer be reproduced directly.** This quiet section did not yet test the yaw disturbance response to a deliberate twist or RC steering.
- The user described a **very slight, low-frequency oscillation** at yaw P=10 (visually estimated at about 2 Hz). On inquiry, it became clear that the term "Drehschwingung" (rotational oscillation) was ambiguous: at first it was unclear whether the vertical axis or the wheel axis was meant; this was then clarified as a back-and-forth tilt about the wheel axis. An exploratory spectral analysis of the readable gyro Z partial lines, performed before the raw file was overwritten, had its strongest component at about 2.8 Hz; because of missing or corrupted serial samples and a recording duration of only about 8.5 s, this is not a precise frequency measurement. The gyro Z RMS value was about 0.028 rad/s, compared with about 0.20 rad/s in the shorter previous yaw-P=0 trace (with different starting conditions). The comparison does not establish an optimal yaw gain, and the gyro Z component does not by itself explain the observed tilting oscillation.
- The user **then explicitly clarified the axis of motion**: the slight oscillation observed visually at yaw P=10 was a back-and-forth tilt about the wheel axis, **not** a visible left-right turning of the direction of travel. The small gyro Z component in the log remains a measurement finding, but it must not be presented as an explanation of the observed tilting oscillation.
- The follow-up test is now stored as `control-live-yaw5.log`. The user had first saved it as `control-live-yaw10-after-fix.log`; the file was renamed after `# CMD YP5` was recognized. The saved trace confirms `PP=6`, `YP=0`, then `YP5` with the response `P: 5.000` before CH5=2. CH5=2 is recorded in readable partial lines from about `30231` to `42109 ms`; a single CH5=1 line lies at the transition before it. From 0.5 s after activation (419 partial lines), roll is −0.34° to +0.46°, the median absolute value 0.13°, gyro Z RMS about 0.024 rad/s, and the raw board voltage minimum 7.241 V. In 255 complete, arithmetically consistent CH5=2 lines, the yaw output is −0.42 to +0.36, and no motor target reaches ±88. An exploratory gyro Z spectral analysis again shows a small component around 2.9 Hz. The conditions and durations of the P=5 and P=10 tests differ, and the P=10 raw file is missing; the numbers alone do not establish a reliable choice between 5 and 10. The slight oscillation described visually at P=10 was later clarified as a back-and-forth tilt about the wheel axis; no direct visual P=5/P=10 comparison exists.

The observations on fast driving and the associated speed and ball-pose code path are documented separately in [Case C](2026-09-27-drive-instability.md).

## Checked so far and still open

**Checked:** CH340/ESP32-S3 communication in sensor diagnostic mode; IMU and SBUS data without actuator load; reappearance of several calibration values after a restart; CH5=1 traces on a stand and on the floor; most recent CH5=1 trace with motor targets within ±88; one CH5=2 comparison trace; `K56` baseline with CH5=0 (raw file later overwritten) and `K56` trace with CH5=2; voltage drop at the pack output according to the user's oscilloscope measurement. The current local source code and the diagnostic scripts are **not committed**; before interpreting any new test, check the state that was actually flashed.

**Not established:** the original working firmware image and its CH5 mode; the actual pack voltage curve and load current; contributions of the wheel motors and leg servos; the physical position of the servo supply bridge; the 5 V and 3.3 V rail voltages during the fault; the ESP32 reset reason and the SBUS failsafe at the time of shutdown; correct signs and scaling of all feedback paths under load; whether the yaw oscillation is excited by the yaw control itself, the angle control, or their interaction; why the return path in the earlier CH5=2 test was recorded as CH5=1 up to the end of the log. The finding "it ran two days ago" should be considered during troubleshooting, but must not be used to rule out a hardware condition that has since changed.

For new recordings: normal firmware over CH340 at **2,000,000 baud**, DTR/RTS off; [capture_balance_trace.py](../../scripts/capture_balance_trace.py) sends the `K56` command with `--trace-mode 56` and stores the column description in the log. The port name may change; [USB/serial notes](../../docs/robot/software/usb-serial-flashing.md) contains the verified settings. Keep new traces under a **new file name** so that the test sequence is preserved.
